# Публикация релизов в Telegram

При публикации GitHub Release в Telegram автоматически уходит пост:
название версии, changelog из описания релиза, кнопка скачивания APK и кнопка перехода
к релизу. Обложка прикладывается, если она есть; если её нет — пост всё равно выходит.
Подходит и канал, и группа: пост уходит от имени бота.

Схема работы:

```text
GitHub Release (Publish release)
        │
        ▼
.github/workflows/telegram-release.yml
        │  (release: published)
        ▼
scripts/telegram-release.mjs
        │  1. берёт release из события GitHub
        │  2. находит APK в ассетах релиза
        │  3. ищет обложку (ассет релиза → release-assets/<тег>/)
        │  4. превращает Markdown из описания в HTML Telegram
        │  5. отправляет sendPhoto/sendMessage (при необходимости — несколькими сообщениями)
        ▼
Telegram (канал или группа)
```

Ничего в приложении, на странице раздачи и в `deploy-pages.yml` для этого не менялось:
workflow — отдельный, зависимости не устанавливает (`npm ci` не нужен), читает только
данные релиза.

---

## Как выглядит пост

Пример реального поста (тег `v1.3.1`):

```text
🚀 SelfCRM 1.3.1

🎛 ГЛАВНЫЙ ЭКРАН: НАПОМИНАНИЯ ПЕРЕЕХАЛИ ПОД ПЛАШКИ

• Плашки «Активные заказы» и «Выручка за месяц» снова стоят первыми, а блок
  «Напоминания» — сразу под ними.
• Между блоками главного экрана появился нормальный отступ (20px)…

📋 ПРОЧЕЕ

• APK: SelfCRM-1.3.1.apk, versionCode 20, versionName 1.3.1, minSdk 24.

📱 Версия 1.3.1

[ 📱 Скачать APK ]  [ 📋 Подробнее ]
```

Заголовки `##` из описания релиза становятся подзаголовками секций (заглавными буквами),
пункты списка — маркерами, `**жирный**` и `` `код` `` — соответствующим оформлением.

## Разовая настройка

### 1. Создать Telegram-бота

1. Откройте [@BotFather](https://t.me/BotFather) и отправьте `/newbot`.
2. Задайте имя (например `SelfCRM Releases`) и username, оканчивающийся на `bot`
   (например `selfcrm_release_bot`).
3. BotFather пришлёт токен вида `123456789:AA…`. Это значение секрета
   `TELEGRAM_BOT_TOKEN` — никому его не пересылайте: тот, кто знает токен, пишет от
   имени бота.

### 2. Добавить бота в канал или группу

1. Создайте канал (или используйте существующий) — публичный с @username или приватный.
   Группа тоже подойдёт: пост уходит от имени бота и виден всем участникам.
2. Канал или группа → «Управление» → «Администраторы» → «Добавить администратора» →
   выберите бота.
3. Обязательное право — **«Публикация сообщений»** (Post messages). Без него Telegram
   вернёт ошибку прав, и workflow упадёт до отправки. В группе админ нужен ещё и потому,
   что права по умолчанию часто запрещают участникам отправку сообщений, а администратор
   это ограничение обходит.
4. Определите `TELEGRAM_CHANNEL_ID`:
   * публичный канал или группа — `@username` (например `@selfcrmtg`);
   * приватный канал — числовой id вида `-1001234567890` (его показывает, например,
     пересылка сообщения канала боту @getidsbot или `getUpdates`).

   Надёжнее указывать числовой id: он не изменится, если вы переименуете @username.

### 3. Добавить секреты в GitHub

Репозиторий → **Settings → Secrets and variables → Actions → New repository secret**:

| Имя секрета | Значение |
| --- | --- |
| `TELEGRAM_BOT_TOKEN` | токен от BotFather (`123456789:AA…`) |
| `TELEGRAM_CHANNEL_ID` | `@username` канала или группы либо `-100…` |

Оба секрета — **Repository secrets**. Больше ничего настраивать не нужно: идентификатор
репозитория и токен для GitHub API workflow берёт сам (`github.repository`, `github.token`).

> Токен и id канала попадают только в переменные окружения шагов и вырезаются из логов
> (`***`). В репозитории, в истории git и в тексте постов секретов нет.

### 4. Проверить без публикации

Actions → **Telegram Release** → **Run workflow**:

* `tag` — оставьте пустым (возьмётся последний опубликованный релиз) или укажите тег;
* `dry_run` — `true`.

В логе появится готовый текст поста и его длина. Секреты на этом шаге не нужны, режим
ничего не отправляет.

### Текущая настройка

| Что | Значение |
| --- | --- |
| Бот | `@selfcrmreleases_bot` |
| Чат | `@selfcrmtg` (супергруппа, id `-1003800511639`) |
| Секреты репозитория | `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHANNEL_ID` — заданы в *Repository secrets* |
| Права бота | администратор в `@selfcrmtg` с правом «Публикация сообщений» |

Бот добавлен администратором, а не обычным участником: в группе права по умолчанию
запрещают участникам писать в чат, администратор это ограничение обходит. В секрете
`TELEGRAM_CHANNEL_ID` указан числовой id — он не изменится, если переименовать группу.

## Как выпустить релиз

1. Поднимите версию и соберите APK — как в [ANDROID.md](../ANDROID.md)
   (`npm run bump -- 1.4.0`, `npm run build`, `npx cap sync android`, `./gradlew assembleRelease`).
2. Приложите обложку (по желанию), см. раздел «Структура изображений».
3. GitHub → **Releases → Draft a new release**:
   * **Tag** — `v1.4.0` (тег создаётся вместе с релизом; префикс `v` обязателен, именно он
     попадает в заголовок поста и в ссылки);
   * **Title** — как показывать релиз на GitHub;
   * **Description** — changelog в Markdown: коротко, чтобы пост читался одним сообщением
     (см. «Формат описания релиза» и «Правило одного поста»);
   * **Assets** — приложите `app-release.apk`; имя файла любое, APK ищется по расширению
     `.apk` (в постах так и были `SelfCRM-1.3.1.apk`);
   * **Set as a pre-release** — можно поставить, пост всё равно выйдет (в заголовке
     появится метка тестирования).
4. **Проверьте, как текст читается в Telegram.** Пока релиз в черновике, проверять нужно
   **файлом**, а не тегом: у черновика нет тега, и `/releases/tags/<тег>` на него отвечает 404.
   Сохраните JSON черновика (id виден в ответе API или в сохранённом `release-id.txt`) и
   прогоните dry-run по файлу:

   ```bash
   curl -s -H "Authorization: token <токен>" \
     "https://api.github.com/repos/doc9830/SelfCRM/releases/<id черновика>" > /tmp/release-<версия>.json
   node scripts/telegram-release.mjs --dry-run --release-file /tmp/release-<версия>.json
   ```

   В выводе должно быть `Сообщений: 1` и подпись ≤ 1024 без «…» — чек-лист в разделе
   «Правило одного поста». Длинное описание сократите здесь же, до публикации релиза.
   Вариант «Actions → **Telegram Release** → **Run workflow** → `dry_run = true`» берёт
   **опубликованный** релиз, поэтому до публикации им проверяют шаблон или готовый файл из
   примера (`--release-file scripts/fixtures/…`).
5. Нажмите **Publish release**. Пока релиз в черновике (draft), пост не выходит: событие
   `published` наступает ровно в момент публикации, когда APK уже приложен.
6. Пост появится в канале или группе через несколько секунд. Ход публикации виден в
   **Actions → Telegram Release** (лог печатает длину каждого сообщения и `message_id`).

> **Ассеты важны до публикации.** Событие `published` — это снимок релиза на момент нажатия:
> ассеты, приложенные после публикации (например, если релиз создан одним запросом к GitHub API,
> а APK и обложка загружены следом), в посте не увидят. В логе появится
> `в релизе v… нет APK`, а кнопка «Скачать APK» заменится ссылкой на страницу релиза.
> Поэтому APK (и обложку, если релиз создаётся без `release-assets/<тег>/`) прикладывайте
> к черновику до **Publish release**.

## Формат описания релиза

Что понимает разбор:

| В описании релиза | В посте |
| --- | --- |
| `## ✨ Что нового` | секция `✨ ЧТО НОВОГО` |
| `- пункт` / `* пункт` | `• пункт` |
| `1. пункт` | пункт с номером |
| `**жирный**`, `*курсив*` | жирный и курсив Telegram |
| `` `код` `` | моноширинный код |
| ```` ```блок``` ```` | моноширинный блок `<pre>` |
| `[текст](https://…)` | ссылка (только `http://` и `https://`) |
| `> цитата` | строки цитаты |
| таблица `\| a \| b \|` | строки `a · b` |

Что не публикуется:

* заголовок `# SelfCRM 1.4.0` — версия и так есть в шапке поста, дублирования нет;
* картинки `![…](…)` — в канал идёт обложка, а не скриншоты из описания;
* «сырой» HTML из описания (`<script>`, `<img>`, `<b>`) — он не исполняется, а показывается
  как текст: пост собирается из экранированного текста.

Рекомендуемый шаблон (он же — то, что видит пользователь в приложении при проверке
обновлений). Описание должно умещаться в **один пост в Telegram** — правило и проверка
описаны в разделе «Правило одного поста»:

```markdown
## ✨ Что нового

- ⌨️ Телефон вводится с цифровой клавиатуры
- 🧮 Количества — только цифры, цены — цифры и точка
- ✅ Настройки проверяют длину ИНН, ОГРН и КПП

## 🔧 Исправлено

- Исправлена обрезка фамилии в карточке клиента

## 📋 Прочее

- APK: `SelfCRM-1.4.0.apk`, versionCode 22. Тесты: 186.
```

Так выглядит готовый пост по этому шаблону (подпись к обложке — 355 из 1024 символов,
одно сообщение, ни одного сокращения):

```text
🚀 SelfCRM 1.3.2

✨ ЧТО НОВОГО

• ⌨️ Телефон вводится с цифровой клавиатуры
• 🧮 Количества — только цифры, цены — цифры и точка
• ✅ Настройки проверяют длину ИНН, ОГРН и КПП

🔧 ИСПРАВЛЕНО

• Исправлена обрезка фамилии в карточке клиента

📋 ПРОЧЕЕ

• APK: SelfCRM-1.3.2.apk, versionCode 21. Тесты: 174.

📱 Версия 1.3.2
```

Если в релизе нет APK, кнопка «Скачать APK» заменяется на «GitHub Release», а в лог
попадает предупреждение — пост всё равно выходит (для строгого режима есть ключ
`--require-apk`).

## Правило одного поста

**Changelog каждого релиза пишется так, чтобы пост в Telegram читался одним сообщением:**
одна обложка, один текст, без второго поста-продолжения, без обрезки слов и без пунктов,
которые переносятся на вторую строку. Нарезка на 2–3 сообщения и короткая подпись
«✨ Новая версия уже доступна!» остались только как аварийный путь — если правило нарушено,
пост всё равно выйдет, но читаться будет хуже.

**Бюджет поста.** Текст с обложкой уходит как подпись к фото, а у подписи лимит 1024
символа (у обычного сообщения — 4096). Значит вся шапка поста должна укладываться
в 1024 символа; рабочий ориентир — до ~900, чтобы остался запас:

| Часть поста | Сколько | Почему |
| --- | --- | --- |
| Заголовок `🚀 SelfCRM 1.4.0` | ~17 | добавляется автоматически |
| Секции | 2–3 | `✨ ЧТО НОВОГО`, `🔧 ИСПРАВЛЕНО`, `📋 ПРОЧЕЕ` |
| Пункты | до 5 | каждый ≤ 80 символов — это одна-две строки на телефоне |
| Строка `📱 Версия 1.4.0` | ~16 | добавляется автоматически |

Итого — 350–500 символов. Именно так выглядит пост из шаблона выше
(`Сообщений: 1`, подпись 355/1024). Если пункты не помещаются в один пост, сокращайте
пункты, а не выпускайте два поста.

**Что считается нарушением и как это видно в логе:**

* больше ~1024 символов — пост станет двумя-тремя сообщениями, а на обложке появится
  краткая шапка (`Сообщений: 2`);
* пункт длиннее 90 символов — в краткой шапке он обрезается с «…», то есть в канал
  уйдёт недописанная фраза.

**Стиль описания.** Секции и порядок те же, что и в предыдущих релизах: `## ✨ Что нового`
(что появилось, по одному факту на пункт), `## 🔧 Исправлено` (что починили),
`## 📋 Прочее` (строка про APK, versionCode и число тестов). Один пункт — одна короткая
фраза с эмодзи в начале (`- ⌨️ …`), без перечислений через запятую, без дублирования версии
в заголовке `#`, без скриншотов и «сырого» HTML. Описание одинаково читается и в приложении
(Проверить обновления), поэтому украшать его в Telegram нельзя.

**Проверять обязательно, до публикации релиза.** Смотрим на сформированный пост, а не на
исходный Markdown:

```bash
# шаблон короткого описания: должно быть «Сообщений: 1», подпись ≤ 1024, без «…»
node scripts/telegram-release.mjs --dry-run --release-file scripts/fixtures/telegram-concise.json

# своё описание: положите его в копию фикстуры (или дождитесь релиза) и проверьте так же
node scripts/telegram-release.mjs --dry-run --tag v1.4.0

# без локального окружения: Actions → Telegram Release → Run workflow → dry_run = true
```

Чек-лист перед нажатием **Publish release**:

- [ ] в dry-run стоит `Сообщений: 1` (а не 2–3);
- [ ] длина сообщения не больше 1024 символов (печатается как `sendPhoto (подпись) — 355/1024`);
- [ ] в тексте поста нет «…» — ничего не обрезано;
- [ ] каждый пункт умещается в одну строку на телефоне (до 80 символов);
- [ ] набор секций и эмодзи совпадает со стилем прошлых релизов;
- [ ] в `📋 Прочее` указаны имя APK, versionCode и число тестов.

## Структура изображений (обложка)

Обложка ищется в таком порядке:

1. ассет релиза с именем `cover.*` — потом `screenshot-1.*`, потом `screenshot*`
   (можно приложить прямо к релизу, без коммитов);
2. файл в репозитории `release-assets/<тег>/` — те же правила имён. Такой файл
   берётся сначала по ревизии тега релиза, а если его там нет — из основной ветки
   (`main`). Поэтому обложку можно добавить и после публикации релиза: пересоздавать
   тег не нужно, достаточно закоммитить картинку в `main`.

```text
release-assets/
└── v1.4.0/
    ├── cover.png          ← уходит в канал как обложка поста
    ├── screenshot-1.png   ← используется, если cover.* нет
    └── screenshot-2.png
```

* Поддерживаются `png`, `jpg`/`jpeg`, `webp`.
* Файлы передаются в Telegram байтами, поэтому внешний хостинг не нужен, а картинка
  не зависит от доступности стороннего сайта.
* Если `<тег>` в `release-assets/` отсутствует или картинок нет — пост выходит без
  обложки (текстом), в лог печатается причина. Каталог создавать заранее не обязательно.
* Обложку лучше держать компактной (до ~5 МБ): Telegram сам сжимает фото, но у него есть
  ограничение на размер файла, и слишком большая картинка приведёт к ошибке отправки
  (`file is too big`).
* Скриншоты (`screenshot-N.png`) используются как обложка только если `cover.*` нет:
  остальные скриншоты в пост не попадают.

## Лимиты Telegram и длинные changelog

| Что | Лимит | Как обходится |
| --- | --- | --- |
| Подпись к фото (обычный пост с обложкой) | 1024 символа | правило: changelog должен умещаться сюда — см. «Правило одного поста» |
| Текст сообщения | 4096 символов | аварийный путь: changelog режется на сообщения по границам пунктов и слов |
| Длина строки | — | длинные пункты переносятся по словам; в краткой шапке пункт обрезается до 90 символов с «…» |

Начиная с релиза 1.3.2 changelog пишется коротко, и пост уходит **одним сообщением**:
обложка с полным текстом и кнопками. Нарезка на 2–3 сообщения осталась страховкой на случай
длинного описания: тогда на фото идёт краткая шапка («✨ Новая версия уже доступна!» и до
четырёх пунктов), а полный текст — следующими сообщениями. Кнопки (`Скачать APK`,
`Подробнее`) прикладываются к сообщению с обложкой, а если обложки нет — к последнему
сообщению: они всегда видны читателю. Разметка (`<b>`, `<code>`, ссылки) при нарезке не
ломается: теги, открытые в одном сообщении, закрываются там же.

## Ручной запуск и перепубликация

Actions → **Telegram Release** → **Run workflow**:

| Параметр | Значение | Что произойдёт |
| --- | --- | --- |
| `tag` | пусто | последний опубликованный релиз |
| `tag` | `v1.4.0` | конкретный релиз (тег должен существовать) |
| `dry_run` | `true` | поста нет, текст печатается в логе |
| `dry_run` | `false` | пост уходит в канал |

Защита от дублей: автоматический запуск по событию сверяется со списком прежних запусков
workflow и, если этот тег уже публиковался успешно (например, вы нажали «Re-run jobs»),
отправка пропускается с сообщением «уже публиковался». Осознанная перепубликация — это
ручной запуск (`Run workflow`): он защиту не проверяет, потому что нажат человеком.

Параллельные запуски по одному тегу не пересекаются: второй встанет в очередь
(`concurrency`), отменить начатую публикацию нельзя.

## Диагностика

| В логе | Причина | Что делать |
| --- | --- | --- |
| `Не задан секрет TELEGRAM_BOT_TOKEN` | секрет не добавлен или переименован | добавьте секрет в Settings → Secrets and variables → Actions |
| `не заданы секреты …` (exit code 2) | запуск без секретов | то же; либо используйте `dry_run=true` — он секретов не требует |
| `Unauthorized` / `401` от Telegram | неверный токен | проверьте `TELEGRAM_BOT_TOKEN` у @BotFather |
| `chat not found` | неверный `TELEGRAM_CHANNEL_ID` | публичный канал или группа — `@username`, приватный — `-100…` |
| `not enough rights to send …` / `Forbidden` | бот не админ или нет права публикации | канал или группа → Администраторы → бот → «Публикация сообщений» |
| `file is too big` | слишком большая обложка | уменьшите картинку в `release-assets/<тег>/` |
| `can't parse entities` | редкая ошибка разбора HTML | проверьте строку из лога; разметка из описания экранируется, поэтому помогает удаление «сырого» HTML из описания релиза |
| `в релизе v… нет APK` | APK не приложен к релизу | приложите файл `.apk` к черновику и опубликуйте релиз (ассеты, добавленные *после* `Publish release`, в пост не попадают) либо запустите workflow вручную с `dry_run=false` — пост выйдет заново, уже с APK |
| workflow не запустился | релиз остался черновиком | нажмите **Publish release** либо запустите workflow вручную |
| `релиз с тегом v… не найден` | опечатка в теге при ручном запуске | укажите существующий тег |

Полный список шагов и точный текст поста удобно смотреть в dry-run: он печатает длину
каждого сообщения, состав кнопок и найденные источник обложки/APK.

## Локальная проверка

Команды работают без секретов и токенов — удобно проверять разметку перед релизом:

```bash
# эталон короткого описания: «Сообщений: 1», подпись ≤ 1024, без «…» (см. «Правило одного поста»)
node scripts/telegram-release.mjs --dry-run --release-file scripts/fixtures/telegram-concise.json

# текст поста из длинной фикстуры (в репозитории: scripts/fixtures/)
node scripts/telegram-release.mjs --dry-run --release-file scripts/fixtures/telegram-release.json

# крайние случаи: спецсимволы, таблица, длинные строки, релиз без APK
node scripts/telegram-release.mjs --dry-run --release-file scripts/fixtures/release-edge-cases.json

# реальный релиз с GitHub (без записи и без секретов)
node scripts/telegram-release.mjs --dry-run --tag v1.3.1

# отключить обложку в проверке / требовать наличие APK
node scripts/telegram-release.mjs --dry-run --release-file scripts/fixtures/telegram-release.json --no-cover --require-apk

# справка по всем ключам
node scripts/telegram-release.mjs --help
```

Полезные ключи: `--skip-sections "Прочее"` — не публиковать служебные секции,
`--max-message` / `--max-caption` — лимиты длины, `--repo` / `--assets-dir` — другой
репозиторий или каталог обложек, `--assets-ref` — искать обложку в конкретной ветке
вместо тега релиза.

## Изменения и отключение

* Тексты шапки и подписи поста, вид секций и подбор имён файлов — в
  `scripts/telegram-release.mjs` (`buildPost`, фрагменты `parseChangelog`).
* Триггеры, список шагов, права и `concurrency` — в
  `.github/workflows/telegram-release.yml`.
* Полностью отключить автопубликацию: удалить workflow-файл либо оба секрета
  (тогда запуск завершится понятной ошибкой и ничего не отправит).
* Секреты хранятся только в GitHub и в логах заменяются на `***`. Токен не нужно (и
  нельзя) вписывать в код, `.env` или описание релиза.

Что workflow делает с файлами репозитория: ничего. Он только читает код и данные релиза;
приложение, страница раздачи (`deploy-pages.yml`) и структура `src/`/`android/` не
затрагиваются.
